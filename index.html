SAGEMCOM EZZAHRA · END-OF-STUDIES INTERNSHIP · WITH ISMAIL JABRI

Intelligent Optical Fiber Tester

Supervised by M. Habib Smei & M. Faouzi Maddouri (ISET Radès) and M. Anis Mdaini (Sagemcom) · PFE code SEM-26-12

ESP32Feasa LED AnalyzerMAX3232TFT Touch (ILI9488/XPT2046) EasyEDA PCBOnshape EnclosureMQTT / Node-REDFirebase Realtime DB

The problem

On Sagemcom's production lines, LED functional tests route light through optical fibers to a Feasa analyzer instead of contact probes — precise, and able to test several LEDs in tight spaces. But fibers wear and degrade with handling, which distorts the RGB and intensity readings. Operators then blame a "faulty LED" when the real culprit is a damaged fiber, causing false rejects, longer test cycles, and lower line throughput.

Objectives

  • Automatically evaluate the condition of a test-bench optical fiber before it's used to qualify a product.
  • Acquire RGB + intensity (RGBI) data from the fiber via the existing Feasa module.
  • Compare live readings against a reference fiber and classify the fiber as conforming or defective.
  • Provide a simple touch interface and a clear visual pass/fail indicator, portable enough for shop-floor use.

How it works

An RGB LED module injects red, then green, then blue light into the fiber under test. The Feasa module reads the light that comes through and returns RGBI values over a serial link. The ESP32 compares each channel's measured intensity to a stored reference (Red 6800 · Green 13000 · Blue 13000) within a ±20% tolerance — the fiber passes only if all three channels are within range. A second RGB LED gives an instant visual verdict: green for conforming, red for defective.

Two diagnostic modes are available: an automatic mode that checks a fiber against the stored reference in one tap, and a manual mode that runs a known-good reference fiber on port 1 alongside the fiber under test on port 2, for direct side-by-side comparison.

PCB & enclosure

The schematic and routing were done in EasyEDA around a deliberately modular design: the ESP32 sits on pin-header sockets and the MAX3232 on an IC socket, rather than being soldered directly — so either can be swapped without reworking the board. RGB channels are protected with 220Ω series resistors; decoupling capacitors sit close to every supply pin. The finished PCB (103×82mm) was fabricated, hand-soldered, and passed every functional test on first power-up.

The enclosure was modeled in Onshape as a two-part 200×125×55mm case: a base holding the PCB, voltage regulator, power jack and ON/OFF switch, and a functional lid cut for the TFT screen, the Feasa module, and a light-guide for the status LED — then 3D printed.

Firmware & software

  • Built with PlatformIO (Arduino framework) in a modular class structure: interface state machine, Feasa communication, LED control, diagnostic logic, WiFi/MQTT, Firebase, and NTP sync each own their responsibility.
  • LovyanGFX drives the touch display; PubSubClient publishes JSON RGBI + diagnostic payloads to the public HiveMQ broker; Adafruit NeoPixel drives both RGB LED modules.
  • A Node-RED dashboard subscribes to those MQTT topics and renders live gauges for both optical ports plus the automatic diagnosis.
  • Results can optionally be persisted to Firebase Realtime Database over HTTPS (no third-party library — raw HTTPClient/WiFiClientSecure), timestamped via NTP and auto-numbered, toggled by a switch right on the touchscreen.

Technical challenge & fix

Early on, the Feasa module simply wouldn't return usable data for the GETRGBI01 command. Digging into the protocol showed the module actually needs an initial capture command ("C") to trigger the photometric acquisition, with a short delay before it's ready — a step that isn't obvious from a first read of the interface. Once the firmware sent C, waited ~2s, then issued GETRGBI01/GETRGBI02, communication became fully reliable over UART2 at 57600 baud (8N1) through the MAX3232 bridge.

PERSONAL / ACADEMIC PROJECT · PROJECT OVERVIEW

Smart Home Automation System

ESP8266/ESP32 · Embedded C

DHT11MQ Gas SensorPIRRelayBuzzerWiFi

Overview

A WiFi-connected home automation and safety controller built around an ESP8266/ESP32, combining automatic door access, environmental monitoring, and intrusion/gas-leak alarms in a single embedded system, programmed in C.

Hardware architecture

  • ESP8266 / ESP32 as the central controller with integrated WiFi.
  • DHT11 sensor for temperature and humidity monitoring.
  • MQ-series gas sensor for leak detection.
  • PIR sensor for motion and presence detection.
  • Relay module driving the door actuator; buzzer and status LEDs for alerts.

Embedded logic & sensor management

Sensors are polled on a loop: DHT11 readings feed the monitoring/control interface; PIR events both automate the door and, when the system is armed, trigger the intrusion alarm; MQ gas readings are checked against a safety threshold that, when crossed, fires the buzzer, cuts the relay-controlled circuit, and raises a notification — independent of the WiFi connection, so the safety response never depends on connectivity.

Technical challenge & approach

Coordinating several sensor types and actuators on a single low-pin-count board while keeping response fast enough for a believable "automatic door," and keeping gas-threshold detection resistant to false positives. The approach: dedicated handling per sensor, tuned thresholds, and a hard separation between the local safety reaction (buzzer/relay) and the networked reaction (notification/control interface).

Skills applied

  • Multi-sensor embedded system design and actuator control on ESP8266/ESP32.
  • WiFi-enabled home-automation architecture in embedded C.
  • Threshold-based safety logic for gas leak and intrusion detection.

PERSONAL / ACADEMIC PROJECT · PROJECT OVERVIEW

RFID Access Control System

Embedded microcontroller · RFID authentication

RFIDUltrasonic SensorLCDServoBuzzerLED

Overview

An RFID-based access control terminal that authenticates presented tags, confirms presence with an ultrasonic sensor, and actuates a servo-driven lock while giving real-time feedback on an LCD with buzzer and LED cues.

Architecture & authentication flow

  • Ultrasonic sensor detects presence at the access point and wakes the system.
  • RFID reader scans the presented tag and checks its UID against an authorized list.
  • A match drives the servo to unlock, shows "Access Granted" on the LCD, and gives a short beep with a green LED.
  • A mismatch keeps the lock engaged, shows "Access Denied," and gives a longer beep with a red LED.

Security & design notes

Access decisions are made only against the defined authorized-UID list, keeping the lock mechanism independent of any external network dependency. Pairing presence detection with identity authentication avoids leaving the reader continuously active and adds a basic layer of tailgating awareness.

Skills applied

  • RFID interfacing and UID-based authentication logic.
  • Sensor fusion (presence + identity) for access control.
  • LCD-driven user feedback and servo-based physical actuation.
